# 0001 入口スキルと小さな機能変更

- 日付: 2026-10-26
- 状態: 採用（初期段階）

## 解消したい問題

製品ごとに開発エージェントの進め方を作り直すと、完了条件と検証結果の結び付きが弱くなる。一方、製品固有の検証コマンドまで共通化すると、対象が増えたときに手順が実態から外れる。

## 決定と理由

`skills/nikostack/` を Agent Skills 形式の唯一の原本とし、Codex と Claude Code の発見場所から相対リンクで参照する。入口は Feature、Bug fix、Review を振り分け、詳細手順は今回必要な小さな機能変更だけを作る。入口には対象プロジェクトを先に読むこと、検証状態を区別すること、費用を意識した委任方針を置く。

製品ごとの Feature Map と操作コマンドは利用先に残す。Niko の `verify-niko` はこの境界を確認するために参照した。言語別の規約は既存の ai-agent-coding-guide を利用し、ここへ複製しない。

共通原本からリンクする方法は、ファイルを二重保守せずにローカルの両ツールへ見せられるため選んだ。現段階で導入スクリプトやプラグインを作っても、二つ目の利用先で必要な差分はまだ分からない。

## 確認と次の判断材料

2026-10-26 時点で、Ruby による YAML frontmatter の解析、原本への二つの相対リンク、Markdown の相対参照先を確認した。Codex CLI 0.164.0 と Claude Code 2.1.310 がローカルにあることも確認した。公式の `quick_validate.py` は PyYAML がないため実行できず、代替確認と区別する。両ツールからスキルを実際に呼び出す確認と、製品の機能変更への適用は未実施である。

次に実際の機能変更へ適用した結果を見て、プロジェクトへの導入方法と検証環境を整えるスキルの形を決める。

適用先が増えて製品固有の例外が繰り返し現れた場合は、共通手順と利用先の手順の境界を見直す。
